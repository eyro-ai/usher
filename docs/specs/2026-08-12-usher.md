# Usher — design

## What it is

Claude is the interface. You ask a question in ordinary language; a set of skills decides which
systems hold the answer, queries them, and replies with citations.

There is no database, no index, and no copy of anything. **Each source stays where it lives and is
queried in place.**

## Principles

1. **Query in place, never copy.** Every source already has search. Copying creates staleness,
   sync, and dedup problems that then need solving.
2. **The router is the index.** The thing worth building is knowing *where* an answer lives.
3. **Cite, don't merge.** Answers name their source and link back. Never blend five systems into
   unattributed narrative.
4. **Nothing is built until search demonstrably fails.**

## Skills

Published to Eyro's internal marketplace, so teammates install and upgrade rather than copy files.

| Skill | Owns |
|---|---|
| `usher` | The router. Decides which sources a question needs, fans out, merges with citations. The only skill anyone needs to remember. |
| `usher-gdrive` | Google Drive — including the Plaud meeting transcripts (see Ingest). |
| `usher-obsidian` | The local vault. Plain markdown, so retrieval is ripgrep over files. |
| `usher-linear` | Issues, projects, cycles. |
| `usher-twenty` | Twenty CRM — people, companies, opportunities, notes. |
| `usher-github` | Repos, pull requests, code. |

Each source skill owns its own auth, quirks, query idioms, and citation format. Sources can be added
or dropped without touching the others.

## Routing

The router's job, and the only real intelligence in the system:

| Question shape | Goes to |
|---|---|
| "What was said / decided in that meeting?" | gdrive (transcripts) |
| "What are my notes on X?" · "What was I thinking about Y?" | obsidian |
| "What's the status of X?" · "Who owns Y?" · "What's planned?" | linear |
| "What happened with customer X?" · "Where did that deal land?" | twenty |
| "How was X implemented?" · "Why does this code do that?" | github |
| "What do we know about X?" (unscoped) | fan out to all five, merge |

Rules:

- **Fan out when unscoped.** A bare topic question hits every source; the cost is latency, and the
  alternative is silently missing where the answer actually was.
- **Refetch, never remember.** Status, ownership, and deal state come from the source on every
  question. The router holds no cache, so it cannot report anything stale.
- **Say what was searched.** Every answer names the sources consulted, so an incomplete answer is
  visibly incomplete rather than looking whole.
- **Empty is an answer.** "Nothing found in Linear or Drive" beats plausible reconstruction.

## Ingest — the one place data moves

Only recordings need moving, because Plaud's own storage is the weak link.

```
Plaud ──Zapier──> Drive: PlaudInbox/     transcripts + summaries, already generated by Plaud
                            │
                  scheduled routine
                            │
              ┌─────────────┼─────────────┐
        Meetings/<category>/          Processed/            Failed/
```

Plaud transcribes and summarizes on its own, so the routine does **not** re-transcribe. It:

1. Assigns a category from a **closed list in the routine's own prompt** — an open-ended one
   invents two hundred near-synonyms within a month.
2. Renames to `YYYY-MM-DD-slug` and files under that category's destination folder.
3. **Moves the original to `Processed/`.** Done means moved: that is the whole idempotency
   mechanism, and it is visible to a human scanning the folder.
4. **Leaves anything it cannot categorize confidently in the inbox.** The inbox is the review queue;
   nothing is guessed into a folder.
5. Moves anything that errors to `Failed/`, never leaving it to retry forever or vanish silently.

**What runs it:** skills need an agent, so the schedule is a cloud routine that invokes Claude and
calls `usher-gdrive`. Not cron, and not code.

### Filing is the user's call, not the system's

There is **no exclusion list**. An earlier draft had one — 1:1s, HR, compensation — inherited from a
design where the KB was shared and the risk was other people reading it. That risk does not exist
here: it is the user's own Drive, under the user's own account.

A tool that refuses to file your own recording into your own folder is overstepping, and a title
pattern is a poor classifier anyway — it will catch "1:1 pricing model" and miss the conversation
that actually mattered.

**Sensitivity is a categorization question.** Each category maps to a destination folder; which of
those folders are private, and which are ever shared, is the user's business. If something
lands in the wrong place, the user moves it — and because nothing is derived from location, moving
it costs nothing.

The one thing the routine will not do is guess. Anything it cannot categorize confidently stays in
the inbox for a human.

## Index

**There isn't one.** Drive full-text indexes its documents, Obsidian is ripgrep over local markdown,
and Linear, Twenty, and GitHub each ship real search. Fanning out across five good search engines is
cheaper and fresher than maintaining a sixth that unifies them.

Revisit only when a real question fails to find a real answer — and then fix the router first.

## Access control

Everything runs under the user's own account, so each agent sees exactly what that person sees. No
tiers, no permission model, no derived index that could leak.

| Source | Identity | Scope |
|---|---|---|
| Google Drive | User OAuth | Their own + shared-with-them |
| Obsidian | Local filesystem | Their own machine |
| Linear | User OAuth | Their teams |
| GitHub | `gh` token | Their repos + org access |
| **Twenty** | **Workspace API key** | **The whole workspace — not user-scoped** |

Twenty is the exception, because its API key is workspace-wide rather than tied to a person. For a
small team this is likely fine; it is recorded so it is a known gap rather than a surprise. If Twenty
gains per-user keys, use them.

## Settings

There is no config file. Working through what actually varies, almost nothing does:

| | Where it lives |
|---|---|
| Drive, Linear, GitHub auth | Ambient — the user's OAuth and `gh` token. There is one Drive: theirs. |
| Twenty's base URL and key | Same for the whole team, so it lives in `usher-twenty` and the environment. |
| Obsidian vault path | The one genuinely per-person value. An environment variable, or the skill asks once. |
| Which sources are enabled | A skill that is not installed is not enabled. |
| Categories and destination folders | Belong to the ingest routine, not the KB — see below. |

A YAML file kept in sync across six skills, to hold one path, is overhead with no reader.

### The routine holds its own settings

Categories and destination folders describe **filing**, not the knowledge base. The router never
needs them: it asks Drive what Drive knows, and whether those documents are meeting notes or
contracts is not its concern.

So they live in the scheduled routine's own prompt, which is the only thing that files anything. If
a teammate wants different folders, they edit their routine — not a shared file that everyone else
also depends on.

## Known risks

- **Fan-out latency.** Five sources per unscoped question. Mitigation is routing well, not caching.
- **Twenty's workspace-scoped key**, above.
- **Category drift** if the closed list is edited casually. It is a schema; treat it as one.
- **Plaud's summary quality is now load-bearing**, since the routine does not re-summarize. If those
  summaries prove thin, add a distillation step — and only then does verbatim-evidence checking
  become relevant again.
