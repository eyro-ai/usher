# Usher — design

## What it is

Claude is the interface. You ask a question in ordinary language; a set of skills decides which
systems hold the answer, queries them, and replies with citations.

There is no database, no index, and no copy of anything. **Each source stays where it lives and is
queried in place.**

## Principles

1. **Query in place, never copy.** Every source already has search. Copying creates staleness,
   sync, and dedup problems that then need solving.
2. **The router is the index.** The thing worth building is knowing *where* an answer lives.
3. **Cite, don't merge.** Answers name their source and link back. Never blend five systems into
   unattributed narrative.
4. **Nothing is built until search demonstrably fails.**

## Skills

Published to Eyro's internal marketplace, so teammates install and upgrade rather than copy files.

Seven skills in **one plugin** — a single install and a single version number. Each loads only when
its description matches the question, so an unused source costs a line in the skill list and nothing
else.

| Skill | Owns | Must not |
|---|---|---|
| `usher` | The router: which sources a question needs, fan-out, merging, the citation contract. The only skill anyone needs to remember. | Query any source itself |
| `usher-gdrive` | **All of Google Drive** — documents, sheets, and the meeting transcripts (see Ingest). | Write |
| `usher-notion` | Notion pages and databases — **workspace content only** (see below). | Write |
| `usher-obsidian` | The local vault. Plain markdown, so retrieval is ripgrep over files. | Write |
| `usher-linear` | Issues, projects, cycles. | Write |
| `usher-twenty` | Twenty CRM — people, companies, opportunities, notes. | Write |
| `usher-github` | Repos, pull requests, code. | Write |

Two boundaries carry the design: **sources never route, and the router never queries.** That is what
lets a source be swapped, disabled, or rewritten without touching anything else.

**Every source is read-only.** This has to be stated because the tokens do not enforce it — Linear's
OAuth, for instance, grants read *and* write, so `save_issue` and `delete_comment` sit in the tool
list. The boundary lives in the skill.

### `usher-gdrive` covers all of Drive — decided 2026-09-02

An earlier draft was inconsistent: the skills table said all of Drive, the routing table said meeting
transcripts only. **Resolved in favour of all of Drive.** A narrow skill would leave ordinary
documents — contracts, specs, sheets — with no source at all, and nothing else would pick them up.

Two consequences to handle when it is built:

- Its `description` must not swallow "where is X documented", which belongs to `usher-notion`.
  Drive holds files; Notion holds written-up knowledge. The boundary is the artefact, not the topic.
- **It must assert which Google account it reached**, not merely that Drive answered. Meeting
  transcripts land in *personal* Drives (see the ingest ticket), so answering from the wrong account
  is more likely here than anywhere else — and, as with Linear, it would produce a wrong answer that
  looks entirely right.

### Notion needs scoping, or it duplicates everything

Notion's own search federates across its connected sources — Slack, Drive, GitHub, Jira, Linear and
more. Left on its default it would return Drive and Linear hits, duplicating two other skills and
citing Notion's copy of something already cited properly.

`usher-notion` therefore searches with `content_search_mode: "workspace_search"` — Notion-native
content only, and faster besides. Non-overlapping sources are what make a merged answer legible.

## Routing

The router's job, and the only real intelligence in the system:

| Question shape | Goes to |
|---|---|
| "What was said / decided in that meeting?" · "Where is that document?" | gdrive |
| "What are my notes on X?" · "What was I thinking about Y?" | obsidian |
| "What's the status of X?" · "Who owns Y?" · "What's planned?" | linear |
| "What happened with customer X?" · "Where did that deal land?" | twenty |
| "How was X implemented?" · "Why does this code do that?" | github |
| "Where is X documented?" · "What does the handbook say?" | notion |
| "What do we know about X?" (unscoped) | fan out to every source that can answer, merge |

Rules:

- **Fan out when unscoped.** A bare topic question hits every source; the cost is latency, and the
  alternative is silently missing where the answer actually was.
- **Refetch, never remember.** Status, ownership, and deal state come from the source on every
  question. The router holds no cache, so it cannot report anything stale.
- **Say what was searched.** Every answer names the sources consulted, so an incomplete answer is
  visibly incomplete rather than looking whole.
- **Empty is an answer.** "Nothing found in Linear or Drive" beats plausible reconstruction.

## Ingest — the one place data moves

Only recordings need moving, because Plaud's own storage is the weak link.

```
Plaud ──Zapier──> Drive: PlaudInbox/     transcripts + summaries, already generated by Plaud
                            │
                  scheduled routine
                            │
              ┌─────────────┼─────────────┐
        Meetings/<category>/          Processed/            Failed/
```

Plaud transcribes and summarizes on its own, so the routine does **not** re-transcribe. It:

1. Assigns a category from a **closed list in the routine's own prompt** — an open-ended one
   invents two hundred near-synonyms within a month.
2. Renames to `YYYY-MM-DD-slug` and files under that category's destination folder.
3. **Moves the original to `Processed/`.** Done means moved: that is the whole idempotency
   mechanism, and it is visible to a human scanning the folder.
4. **Leaves anything it cannot categorize confidently in the inbox.** The inbox is the review queue;
   nothing is guessed into a folder.
5. Moves anything that errors to `Failed/`, never leaving it to retry forever or vanish silently.

**What runs it:** skills need an agent, so the schedule is a cloud routine that invokes Claude and
calls `usher-gdrive`. Not cron, and not code.

### Filing is the user's call, not the system's

There is **no exclusion list**. An earlier draft had one — 1:1s, HR, compensation — inherited from a
design where the KB was shared and the risk was other people reading it. That risk does not exist
here: it is the user's own Drive, under the user's own account.

A tool that refuses to file your own recording into your own folder is overstepping, and a title
pattern is a poor classifier anyway — it will catch "1:1 pricing model" and miss the conversation
that actually mattered.

**Sensitivity is a categorization question.** Each category maps to a destination folder; which of
those folders are private, and which are ever shared, is the user's business. If something
lands in the wrong place, the user moves it — and because nothing is derived from location, moving
it costs nothing.

The one thing the routine will not do is guess. Anything it cannot categorize confidently stays in
the inbox for a human.

## Index

**There isn't one.** Drive full-text indexes its documents, Obsidian is ripgrep over local markdown,
and Linear, Twenty, and GitHub each ship real search. Fanning out across five good search engines is
cheaper and fresher than maintaining a sixth that unifies them.

Revisit only when a real question fails to find a real answer — and then fix the router first.

## Access control

Everything runs under the user's own account, so each agent sees exactly what that person sees. No
tiers, no permission model, no derived index that could leak.

| Source | Identity | Scope |
|---|---|---|
| Google Drive | User OAuth | Their own + shared-with-them |
| Notion | User OAuth | The pages they can open |
| Obsidian | Local filesystem | Their own machine |
| Linear | User OAuth | Their workspace |
| GitHub | `gh` token | Their repos + org access |
| **Twenty** | **Workspace API key** | **The whole workspace — not user-scoped** |

Twenty is the exception, because its API key is workspace-wide rather than tied to a person. For a
small team this is likely fine; it is recorded so it is a known gap rather than a surprise. If Twenty
gains per-user keys, use them.

## Configuration — discovery for candidates, settings for intent

Most values a skill needs have an authoritative home elsewhere, and reading them there beats
remembering them:

| Value | Discovered from |
|---|---|
| Twenty base URL and key | The environment, else a `.env` recorded in settings |
| GitHub owner | The repository in the question, else the repo in hand, else `gh api user/orgs` |
| Linear workspace | The connector |

**But discovery answers "what exists", not "what should be searched".** Those are different
questions, and some sources need the second one answered.

Obsidian is the case that proved it. Its registry lists every vault the user has ever opened —
including another company's. No amount of discovery tells the skill to leave that one alone; the
`open` flag reflects what Obsidian happens to have open, not intent. Only the user can say which
vaults Usher should read.

So: **`~/.usher/settings.json`**, user-scoped, outside the plugin (which is replaced on upgrade) and
outside the repo (it is per-person).

```json
{
  "version": 1,
  "obsidian": { "vaults": ["/Users/someone/Documents/Vault"] },
  "twenty": { "env_file": "/Users/someone/Projects/crm/.env" }
}
```

**No setup step.** Whichever skill needs a value asks for it on first use and writes it. Nothing has
to be run before a first question.

The file's format is a contract every skill must follow, so it lives where skill authors read —
`CLAUDE.md`. It is not restated here; one home per fact.

### A source that cannot answer is simply absent

Without a settings file there is no `enabled` flag, and none is needed. A source that has no
credentials, no connector, or nothing to discover cannot answer — which is indistinguishable from
not having it. Treat the two the same:

- **Never configured** — omit it. No mention, no noise. Someone with no Twenty account should never
  read the word Twenty.
- **Configured but failing right now** — report it with the fix: `linear(unavailable) — run /mcp to
  reconnect`. This is a source that normally works, so its absence is information.

The difference is whether the source has ever answered, not a flag someone set. "What can Usher see
right now?" is answered by asking it, not by reading a file.

## Known risks

- **Fan-out latency.** Up to six sources per unscoped question. Mitigation is routing well and
  disabling what you do not use — not caching.
- **Discovery drift.** If Obsidian changes its registry format or Twenty moves its env var names,
  a source goes quiet. The failure is visible — the source simply stops appearing — but the cause is
  not, so a source that silently stops answering is worth checking here first.
- **Notion federation overlap.** If `usher-notion` ever loses its `workspace_search` scoping it will
  silently start duplicating Drive, GitHub and Linear results under Notion citations.
- **Twenty's workspace-scoped key**, above.
- **Category drift** if the closed list is edited casually. It is a schema; treat it as one.
- **Plaud's summary quality is now load-bearing**, since the routine does not re-summarize. If those
  summaries prove thin, add a distillation step — and only then does verbatim-evidence checking
  become relevant again.
